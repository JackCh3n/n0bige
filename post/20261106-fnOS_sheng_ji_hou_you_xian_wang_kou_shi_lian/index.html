fnOS升级后有线网口失联

Posted on 2026-11-06 Edited on 2026-11-09 In 技巧 , 问题 , 错误 Views: Word count in article: 1.8k Reading time ≈ 7 mins.

防坑指南：fnOS/Docker 宿主升级换内核后「有线网口失联、备用口正常」（OVS 内部端口丢失）

适用场景：宿主通过 Open vSwitch 桥接物理网口（有线 IP 配在 OVS internal 口上）， 系统升级/换内核重启后，有线 IP 完全不通，但另一张网卡（WiFi/备用口）的管理页和 SSH 一切正常。本文以飞牛 fnOS 为例，适用于任何同构环境。 全部命令与输出均来自真实故障的定位与修复过程，可直接照抄执行。

1. 症状（对照自查）

现象 判据
有线 IP 完全不通 ping 100% 丢包、SSH 全端口超时、连 TCP SYN 都没有回应
备用口/WiFi 侧一切正常 管理页可打开、SSH 可登录、延迟正常（同机房 1~2ms）
「时好时坏/像断连」 双默认路由下，出方向流量仍优先走死掉的有线路由
本机自查：网关 ARP 解析不到 ip neigh show 里网关为 INCOMPLETE
重启无效 重启后依然不通（问题出在启动流程，不在运行态）

2. 快速定位（5 分钟五步走）

第 1 步：确认物理链路没坏

载波=1、无错误计数 → 网线/交换机/网卡硬件没问题，问题在软件层，继续往下。

第 2 步：排除防火墙（很多人第一反应是防火墙，先排除掉）

判据：INPUT 链 policy 为 ACCEPT、且没有针对本机端口的 DROP/REJECT 规则 （若宿主跑了 Docker，只会看到 DOCKER 系列的 NAT/桥接规则——那是正常的，不拦 INPUT）。 本文案例的规则集里只有 Docker 标准规则，INPUT ACCEPT → 排除防火墙。

第 3 步：看网关 ARP（关键证据）

问题案例的实际输出：

网关 ARP 为 INCOMPLETE —— 物理口有载波却连二层都通不了， 说明包根本没从接口发出去/进来。这是「OVS 数据面丢端口」的典型信号。

第 4 步：检查 OVS 数据面（实锤）

问题案例的实际输出：

两个异常一目了然：

  1. 端口列表里只有物理口，没有 internal 口（本应同时有 port N: <物理口> 和 port M: <有线口>-ovs (internal)）；
  2. missed/lost 计数暴涨（18 万+）——物理口收到的包没有去处，直接丢。

第 5 步：对照 OVSDB 配置与守护进程

问题案例：ovs-vsctl show 里桥和端口配置齐全、ovsdb-server/ovs-vswitchd 进程也在、服务显示 active——配置没丢，是数据面没有随新内核正确重建。

3. 根因

宿主（fnOS）系统更新触发换内核并重启后：

  1. OVS 内核数据面（ovs-system）在新内核上重建；
  2. 重建时只挂回了物理口，internal 口（有线 IP 所在的口）没有重新挂进数据面；
  3. OVSDB 配置还在，所以 ovs-vsctl show 看起来一切正常；
  4. 于是「配置正常、数据面缺端口」——有线口收到的包全部 missed → lost，有线 IP 完全失联；备用口不受影响。

触发条件：fnOS 升级 → 换内核版本 → 重启。重启一次未自愈， 再重启一次也未自愈（两次实测），说明是升级遗留的确定性问题， 等待官方修复前需手工恢复。

6. 防复发与应急

  1. 应急入口：给宿主保留第二张网卡（WiFi/USB 网卡均可，DHCP 即可）。 有线挂掉时，备用口的管理页/SSH 就是唯一入口——没有它只能接显示器键盘。
  2. 每次换内核重启后，先 ping <网关> 验证有线口，不通就执行第 4 节命令。
  3. 双默认路由的坑：有线与备用口各有一条默认路由时， 有线路由优先级更高（无 metric 默认最优先）。有线坏了以后系统仍优先走死路由， 这就是「时好时坏」的来源；需要时可在有线恢复后 ip route del default via <有线网关> dev <有线口>（重启失效，仅临时缓解）。
  4. 向系统厂商反馈：升级换内核后 OVS 数据面未重新挂载 internal 口， 属于其网络服务在换内核场景下的缺陷。

坑 报错/现象 一句话解法
